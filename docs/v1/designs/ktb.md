# KtB（选手端）设计文档

对于选手端（Kessoku the Broadcaster，简称 KtB），初步设计是实现一个 Electron 应用。安装并运行在选手比赛的机器上，用于实时推流数据到服务端，并由服务端转发所需视频流到导播端编排。

## 功能简介

选手端应用通过 `RL 比赛 ID`、`用户 ID`、`用户推流 token` 来连接到服务器。

通过 WebSocket（socket.io）连接，由 socket.io 库来确保自动重连、心跳检测等功能。

在连接状态下，服务端将会可能下发指令，遥控选手端软件进行视频流的传输或中止。可能的指令：

- 开始传输指定分类的视频流
- 停止传输指定分类的视频流
- 传输指定分类的最近某个时长的本地视频缓存

由于这个连接是双向的，选手端也可以主动发送指令。可能的指令：

- 就绪，并发给服务器部分自身配置
- 停止就绪状态

视频流传输使用 WebRTC 协议，同样使用一些参数建立连接。它是独立的一个传输，而非使用主体的这个 socket.io 连接来传输。

## 用户界面功能

选手端启动时，显示上述关键参数的登录界面来连接，并具备合适的提示交互。

连接后，界面会显示当前登录并匹配到的 RL 侧选手信息以方便核对。之后就可以配置多个要传输的视频流，并看到预览。默认行为是：初始自动添加一个屏幕捕捉的视频流并有一个分类的 id（如 `screen_capture`，默认为显示器 0 的全屏，可以修改；如检测到摄像头存在，则添加第二个视频流，同样可以修改。选手端上可以添加/删除/修改这些要传输的视频流。视频流需要具备分类 ID，以及其他的一些此分类自身的内部配置字段，如显示器序号、视频输入源的相关参数、输出分辨率、推流分辨率、输出码率、推流码率等（都有默认值）。

在确认配置 OK 后，可以保存设置并点击按钮确认锁定配置并进入赛时就绪受控状态。这样此选手端软件会隐藏到托盘，后台工作，但通过托盘可以重新打开主界面。如果要修改配置，需要先停止受控状态。

如果发生意外情况（多是网络问题）断连，尝试带 delay 的无限次数的自动重连，除非服务端明确返回诸如 token 不正确等拒绝信息。

未来的进阶 features：

- VRR 可变码率和压缩
- 服务端下发统一配置减轻配置工作量
- 配置防选手修改

## 高阶功能和 API

命令行参数：

- `d, --deamon`：后台静默启动，不显示 UI，直接隐藏到托盘并自动就绪锁定
- `—-silent`：即使出现错误（如 token 不对）导致无法登录或无法推流，也不弹出 UI，仅记录日志

配置文件：

程序的配置文件需要写入到一个比较 public 且固定的位置，如 `~/.{appName}/conf.json`，应用每次修改配置就写入这个文件，而每次启动时读这个文件来加载配置，并且启动后注册一个  watcher，监听配置文件修改，如果被外部修改，且有实际的配置变化，则保持当前状态的前提下重载（例如当前是就绪已推流，则要按新配置重新推流）。这样允许高级用户程序化地生成或实时修改配置。

应用程序设置项：

- 开机自启动（默认关闭）

这些高阶功能的使用场景是，为减轻人工配置工作量，对于区域赛，配置人员可能通过自行制作系统镜像或同传，来提前把一台配置好的机器上的系统，快速复制给其他机器。因此，他们可能希望的自动化配置的方式是：在恢复镜像的其他 n-1 台选手机上，通过某种姿势，如自动网络下发或人工，为每台新机器写入 unique 配置（如主机名、座号等）。这些特异配置当然也包括我们这个应用的选手端配置（他们需要自己修改配置文件里的 token、userId 等字段）。之后它们的脚本会执行程序，以后台模式启动。这样选手机器哪怕关机重启，也可以自动恢复会话。
